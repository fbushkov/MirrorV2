# Архитектура сайта и платформы Mirror V2

_v0.1 · 2026-10-27. Владелец документа — агент `mirror-architect`. Решения с последствиями оформляются ADR в `docs/adr/`._

Документ описывает, как растёт сайт: от маркетинговых страниц сейчас к приёму заявок, личному кабинету клиента
и админке. Архитектура агентов **внутри продукта** (парсер, аналитик, отчёты) — отдельно, в `docs/architecture/agents.md`.

## 1. Этапы развития

| Этап | Что появляется | Статус |
|---|---|---|
| **1. Маркетинговый сайт** | многостраничный сайт по макету Figma, тексты, демо-дашборды на демо-данных | идёт |
| **2. Приём заявок** | форма → сервер → БД → письмо команде; согласие по 152-ФЗ; антиспам | следующий |
| **3. Отчёт внешнего анализа** | демо-отчёт в фиолетовом направлении (`/hr-brand`) на основе старого «Экспресс-аудита»; отчёт клиенту — PDF по почте (ADR-0007) | после 2 |
| **4. Админка (для команды Mirror)** | заявки и статусы, загрузка выгрузки парсера, генерация и выпуск отчёта | когда отчётов станет много |
| **5. Личный кабинет клиента** | вход, отчёты онлайн, дашборд здоровья культуры на реальных данных | **отложен** (решение 2026-10-27: достаточно отчёта) |
| **6. Агенты продукта** | выгрузка парсера → ИИ формирует отчёт → проверка экспертом | см. `agents.md` |

Каждый следующий этап не ломает предыдущий: маркетинговые страницы остаются статическими (prerender), а
динамическое живёт в отдельных зонах маршрутов.

## 2. Зоны маршрутов (App Router, route groups)

```
src/app/
  (site)/                 маркетинговый сайт: общая шапка и подвал, всё статическое
    page.tsx              /
    about/ pricing/ start/ hr-brand/(demo, methodology) culture-health/(demo, methodology) docs/[slug]/
  (cabinet)/app/          личный кабинет клиента — /app/*        (этап 4)
  (admin)/admin/          админка команды Mirror — /admin/*       (этап 3)
  api/                    Route Handlers: вебхуки, healthcheck, приём данных парсера
  sitemap.ts robots.ts    из карты маршрутов ROUTES
```

- У каждой группы свой `layout.tsx`: у сайта — Header/Footer из макета, у кабинета и админки — своё меню, без маркетингового подвала.
- `/app` и `/admin` закрываются в `proxy.ts` (так в Next 16 называется бывший middleware) и **ещё раз** на сервере в каждом обработчике: проверка в proxy — только удобство, не защита.
- `/app` и `/admin` — `noindex`, не попадают в sitemap.
- Перенос текущих страниц в `(site)` — без смены адресов; делаем вместе с переносом главной по макету.

## 3. Слои кода

```
src/
  app/                    только маршруты: собирают страницу из секций, задают metadata
  components/
    ui/                   shadcn, подогнанный под размеры макета (кнопки 48, поля, бейджи)
    site/                 общие блоки сайта: Header, Footer, PageHero, Section, Breadcrumbs, Card…
    charts/               ECharts-обёртка и тема
    <домен>/              блоки одной страницы/домена (home, pulse, start…)
  content/                тексты и демо-данные; ROUTES/NAV/FOOTER в site.ts — единственная карта ссылок
  lib/                    чистые функции без сервера: typograf, форматирование, валидация (общие схемы Zod)
  server/                 (появится на этапе 2) только серверный код, import "server-only"
    db/                   схема, миграции, клиент
    leads/                приём заявок: сервис, уведомления
    auth/                 сессии, роли (этап 3–4)
    parser/               адаптер к данным существующего парсера (только чтение)
```

Правила:
- Компоненты не ходят в БД напрямую — только через функции `src/server/*`.
- Схемы валидации (Zod) лежат в `src/lib/schemas`, одна схема на клиенте и сервере.
- Тексты не хардкодятся в страницах; короткие слова в текстах связываются неразрывным пробелом через `typograf()` (`src/lib/typograf.ts`).
- Ссылки только из `ROUTES` (`src/content/site.ts`); в разметке нет `href="/..."` руками, кроме якорей внутри страницы.

## 4. Приём заявок (этап 2)

```
Форма (client) ──Server Action──▶ validate (Zod) ─▶ антиспам ─▶ БД: leads + consents ─▶ outbox
                                                                              │
                                              воркер/cron ◀──────────────────┘
                                                 ├─▶ почта команде (SMTP)
                                                 └─▶ Telegram-бот команды
```

- **Server Action** для формы на сайте; Route Handler `/api/leads` — только если понадобится приём извне.
- **Антиспам:** скрытое поле-ловушка, минимальное время заполнения, лимит запросов по IP; при атаке — Яндекс SmartCaptcha.
- **Идемпотентность:** ключ отправки из формы; повторный сабмит не создаёт дубль.
- **Outbox:** заявка сохраняется всегда, даже если почта или Telegram недоступны; уведомления дошлёт воркер. Ни одна заявка не теряется.
- **152-ФЗ:** храним факт согласия: версия текста согласия и политики, время, хэш IP. Данные — на серверах в РФ. Минимум полей. Персональные данные не пишутся в логи.
- **Ответ пользователю** — экран «Заявка принята» без перезагрузки; при ошибке — текст ошибки и контакты.

## 5. Данные (этапы 2–4)

Postgres (как в старом проекте). ORM — решить в ADR-0003 (кандидаты: Drizzle — схема в TS и SQL-миграции; Prisma).

| Таблица | Этап | Назначение |
|---|---|---|
| `leads` | 2 | заявки: тема, компания, контакт, комментарий, источник страницы, UTM, статус |
| `consents` | 2 | согласия: lead_id, версия документа, время, ip_hash |
| `outbox` | 2 | очередь уведомлений с попытками |
| `companies` | 3 | компании-клиенты (tenant) |
| `users`, `memberships` | 3–4 | пользователи и их роль в компании |
| `reports`, `report_versions` | 3–4 | опубликованные отчёты внешнего среза |
| `audit_log` | 3 | кто что сделал в админке и кабинете |

Данные парсера приходят **выгрузкой файлом**, где всё уже собрано и размечено (решение 2026-10-27). Адаптер
`src/server/parser` читает файл и проверяет его схемой Zod; по нему ИИ формирует отчёт (ADR-0007). Формат выгрузки — описать
по образцу файла, когда он будет. Имена авторов отзывов в отчёт не переносим.

## 6. Доступы (этапы 3–4)

- **Вход:** ссылка на почту (без паролей) для клиентов; для команды — то же плюс 2FA позже. Сессия в httpOnly-cookie.
- **Роли:** `mirror_admin`, `mirror_expert` (команда); `client_owner`, `client_viewer` (клиент).
- **Изоляция клиентов:** каждый запрос к данным фильтруется по `company_id` из сессии на сервере; ID из URL не доверяем.
- **Правило 5 человек** для дашборда здоровья культуры проверяется **на сервере** при выборке, а не скрывается в интерфейсе.
- Все действия в админке и выгрузки — в `audit_log`.

## 8. Окружения и деплой

- `development` (локально), `production`. Хостинг — **REG.RU, сервер администрирует пользователь сам** (ADR-0006).
- docker compose на VPS: Next.js `output: "standalone"` + Postgres + nginx (HTTPS, Let's Encrypt); переменные — в `.env.example` без значений.
- Письма — через SMTP почты на домене (сервер в РФ).
- Логи — JSON в stdout; персональные данные маскируются.
- Заголовки безопасности в `next.config.ts` (`headers()`), до запуска формы: CSP (с учётом ECharts и Яндекс Метрики),
  `frame-ancestors 'none'`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Content-Type-Options: nosniff`.
- CI без секретов и с правами `contents: read`; деплой — отдельным workflow с `environment` и защитой веток.
- Требования 152-ФЗ к заявкам и кабинету — в ADR-0003 и ADR-0004.

## 9. Открытые вопросы

1. Тариф REG.RU (VPS или облачный сервер), ОС, есть ли уже Docker; почтовый ящик для заявок и SMTP.
2. ORM — ADR-0003, решаем перед этапом 2.
3. Образец выгрузки парсера — чтобы описать схему файла.
4. Структура нового отчёта: какие из 14 разделов старого «Экспресс-аудита» оставляем и как связать с индексом, слепыми зонами и местом в отрасли.
