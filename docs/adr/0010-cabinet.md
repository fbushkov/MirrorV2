# 0010. Личный кабинет: вход, роли, подразделения, опросы, хранение
- Статус: принято · Дата: 2026-11-01 · Кто: пользователь (кабинет для клиентов внутреннего анализа, один эксперт, мобильная версия),
  пользователь по рекомендации Claude (опрос по ссылке на подразделение, дерево ведёт клиент, сроки хранения); технические
  выборы (своя реализация входа, Drizzle) — предложено, утверждаются в начале разработки.
- Заменяет ADR-0004: его требования вошли сюда и дополнены.

## Контекст
Кабинет получают клиенты диагностики и кампании, запуск — к первому договору на внутреннюю услугу. Продуктовое описание —
`docs/product/cabinet.md` (версия 0.3). Отчёты — неизменяемые версии JSON по схеме (ADR-0009). Сервер на REG.RU ведёт
пользователь (ADR-0006), эксперт в Mirror один. Значит: минимум зависимостей и ручной работы, приватность — на сервере.

## Решение

### 1. Зоны и страницы
- `(cabinet)/app/*` — кабинет клиента, `(admin)/admin/*` — админка эксперта. Страницы на React, классы и графики прототипа (ADR-0008),
  поведение элементов — Radix. Рендер динамический, `noindex`, вне `sitemap`.
- Страницы для сотрудников без входа: `/c/[company]/decisions` (опубликованные решения), `/s/[token]` (опрос), `/f/[token]` (анонимная форма).
  `noindex`; токены случайные, 128 бит.
- Адаптивность с первой версии: 390 px без горизонтальной прокрутки, как у сайта.

### 2. Вход и сессии (из ADR-0004)
- Без паролей: одноразовая ссылка на почту, живёт 15 минут, в БД — хэш токена. Ссылка открывает страницу с кнопкой «Войти»,
  вход по POST: почтовые сканеры не сжигают токен. Лимит запросов на адрес и IP, одинаковый ответ для известных и неизвестных адресов.
- Сессия на сервере (таблица `sessions`), новый идентификатор после входа, тайм-аут простоя 30 дней для клиентов и 12 часов для команды;
  cookie `__Host-`, `Secure`, `HttpOnly`, `SameSite=Lax`. Отзыв сессий — при удалении из команды.
- Команда Mirror: вход по ссылке плюс TOTP-код (2FA) обязательно.
- Реализация своя, в `src/server/auth`: требования узкие (нет паролей и внешних входов), а своя реализация — меньше зависимостей
  на сервере, который ведёт один человек. TOTP — проверенная библиотека, не своя криптография. *Предложено.*

### 3. Роли и права
| Роль | Область |
|---|---|
| `mirror_expert` | Все компании (эксперт один) |
| `mirror_admin` | Все компании, запасной доступ владельца сервиса |
| `client_owner` | Своя компания, управление командой и настройками |
| `client_hrbp` | Своя компания, все группы, сигналы, ведение решений и плана |
| `client_manager` | Ветка дерева от своего подразделения |
| `client_executive` | Компания и первый уровень подразделений, без ленты сигналов |
| `client_viewer` | Обзор и отчёты PDF |

- `memberships(user_id, company_id, role, unit_id)`: `unit_id` обязателен для `client_manager`. Один человек — в нескольких компаниях.
- Все проверки прав — в одной функции `can(session, action, resource)` (`src/server/auth/policy.ts`) по матрице из `cabinet.md`, раздел 4.
  Страницы и обработчики не проверяют роли сами.
- Если экспертов станет больше — таблица назначений компаний, остальная модель не меняется.

### 4. Изоляция компаний
- `company_id` берётся только из сессии; идентификаторы из адреса проверяются на принадлежность компании.
- Второй уровень — Postgres RLS: в транзакции ставится `app.company_id`, политики на всех таблицах клиента.
- Тесты на подмену чужого идентификатора (IDOR) для каждого маршрута кабинета обязательны (ADR-0005).

### 5. Дерево подразделений
- Ведёт клиент: загрузка таблицы «подразделение, входит в, численность» или правка в настройках; эксперт проверяет при запуске.
- Версии: `unit_versions(company_id, version, created_at, frozen_by)` и `units(version_id, id, parent_id, name, size)`.
  Правка создаёт черновик новой версии. Запуск волны замораживает действующую версию, черновик вступает со следующей волны.
- Отчёт хранит снимок дерева, по которому посчитан (`internal.units`), поэтому старые отчёты не меняются при реорганизации.
- Подразделение меньше 5 человек помечается при загрузке.

### 6. Правило 5 человек на сервере
- Кабинет показывает только срезы, заранее посчитанные в отчёте (`internal.slices`). Произвольных запросов к сырым данным нет.
- Правило считается по **ответившим**, а не по численности: в подразделении из 85 человек трёх ответивших легко узнать.
  Схема отчёта не принимает балл, если ответили меньше 5 (ADR-0009). Уверенность среза — по доле ответивших.
- **Защита от вычитания** — при расчёте срезов: если родитель минус видимые дочерние группы даёт 1–4 человека,
  скрывается ещё одна дочерняя группа (дополнительное скрытие). То же для этапов жизненного цикла внутри подразделения.
  Функция `complementarySuppression()` — в `src/lib/report/methodology.ts`, схема проверяет результат, всё с тестами.
- Руководитель получает срезы только своей ветки: сервер фильтрует по поддереву `memberships.unit_id` в версии дерева отчёта.

### 7. Опросы и анонимная форма
- **Одна ссылка на подразделение и волну**: `survey_links(wave_id, unit_id, token)`. Компания рассылает сама.
- Ответ хранит волну, подразделение и ответы. Не хранит IP, адрес, браузер, время с точностью выше дня.
- Повторы: подписанная cookie на волну (один ответ с браузера); лимит частоты по хэшу IP с солью волны, хэши удаляются
  после конца волны; флаг «ответов больше численности» — подразделение проверяет эксперт до публикации.
- Анонимная форма: `/f/[token]` на компанию; сообщение обезличивается при приёме (имена и персональные сведения убираются)
  и проверяется экспертом, прежде чем попасть в анализ. В подразделения анонимные сообщения не попадают.
- Импорт из каналов компании: файл, хэш, проверка формата, обезличивание до записи в `raw_*`.

### 8. Хранение и удаление
- Сырые ответы и сообщения — отдельная схема БД `raw`, доступ у обработки и эксперта, не у клиентов.
- Удаление по расписанию: сырые данные — в течение 30 дней после публикации итогового отчёта услуги (152-ФЗ, ст. 21 ч. 4:
  цель достигнута); данные компании — через 6 месяцев после окончания договора (кабинет это время только для чтения,
  клиент получает архив PDF), учётные записи — в течение 30 дней после закрытия кабинета. Каждое удаление — акт и запись
  в журнале (приказ Роскомнадзора № 179). Полная таблица сроков — `docs/product/business-rules.md` §5.1.
  *Изменено 2026-11-01: было 90 дней после окончания услуги.*
- Отчёты, агрегаты, проверенные цитаты хранятся, пока действует договор и период чтения.
- Сроки проверяет юрист до первого договора; в договор-поручение (152-ФЗ, ст. 6 ч. 3) включаются эти сроки и порядок удаления.
- Бэкапы в РФ, зашифрованы; сырые данные в бэкапах живут не дольше срока бэкапов.

### 9. Журнал действий
`audit_log` только на добавление (права `INSERT` без `UPDATE`/`DELETE`): входы, просмотры отчётов и срезов, выгрузки,
изменения команды, ролей, дерева, решений, публикации, удаления.

### 10. Ход работы и письма
- `engagements(company_id, service, status, started_at, due_at)` и `engagement_stages(engagement_id, stage, at, by)`.
  Этапы ставит система по событиям админки (опрос запущен, отчёт опубликован), вручную — «эксперт проверяет» и «встреча проведена».
- Письма — через `outbox` и SMTP (ADR-0003). Клиентам изнутри — без цифр по группам. Внешним клиентам — те же этапы письмами.

### 11. Данные
Таблицы: `companies`, `unit_versions`, `units`, `users`, `memberships`, `sessions`, `login_tokens`, `subscriptions`,
`engagements`, `engagement_stages`, `reports`, `report_versions`, `decisions`, `plan_steps`, `meetings`, `surveys`,
`survey_waves`, `survey_links`, `raw.responses`, `raw.messages`, `imports`, `documents`, `notifications`, `outbox`, `audit_log`.
ORM — Drizzle (ADR-0003), миграции SQL в git. *Предложено.*
Дополнено ADR-0011: `engagements.phase`, `engagement_tasks`, `unit_versions.approved_at`, `questions`, `question_answers`, `expert_slots`.

## Последствия
- Кабинет и админка делаются вместе: без админки отчёты некому публиковать.
- Первая очередь (к диагностике) и вторая (к кампании) — `cabinet.md`, раздел 12.
- Нужны тесты: права по матрице ролей, IDOR, правило 5 и дополнительное скрытие, удаление по срокам, отсутствие IP в ответах опроса.
- Перед запуском — проверка `mirror-security` и юриста (сроки, договор-поручение).
- `docs/architecture/site.md`, раздел 6, ссылается на этот ADR.

## Альтернативы
- Одноразовые ссылки опроса: защищают от повторов, но их раздаёт компания и может записать, кому какая досталась. Отложено как отдельная услуга.
- Готовая библиотека входа (Auth.js, better-auth): быстрее старт, но больше зависимостей и меньше контроля над сессиями и RLS при узких требованиях.
- Произвольные фильтры по сырым данным в кабинете: гибче, но правило 5 и защиту от вычитания пришлось бы проверять на каждый запрос.
  Готовые срезы в отчёте проще проверить и объяснить.
- Дерево ведёт эксперт: точнее, но съедает время единственного эксперта и отстаёт от реорганизаций клиента.
